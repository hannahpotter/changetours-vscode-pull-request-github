# Change Tour Schema

Every valid `.changetour.md` file has three parts.

**Part 1: YAML frontmatter** binding the tour to a PR (required, must be the first lines of the file):

```
---
schemaVersion: 1 <used for mitgrations - currently must be 1>
prNumber: <integer>
prOwner: <github owner>
prRepo: <github repo>
baseSha: <PR base commit SHA at tour-author time>
headSha: <PR head commit SHA at tour-author time>
---
```

**Part 2: A single H1 title** (`# ...`).

**Part 3: An ordered tree of three node kinds.**

- **group**: a markdown heading `##` through `######` that groups related nodes. To mark a section as collapsed-by-default in the viewer, append an HTML comment: `## My Section <!-- collapsed -->`.
- **text**: a paragraph of narration
- **hunk**: a `<details>` block referencing one diff hunk from the bound pull request. The on-disk shape is GitHub-friendly so the file renders as a collapsible syntax-highlighted diff in standard markdown viewers:

````
<details open>
<summary><code>path</code> · One-line summary</summary> (with <code>old</code> → <code>new</code> for renames)

<!-- changetour:hunk file="repo/relative/path" [previousFile="old/path"] [highlights="new:14-18,old:22-25"] [summary="authored one-line summary to override auto-fallback"] [baseBlob="<git blob SHA>"] -->

```diff
@@ -A,B +C,D @@
<full raw patch body>
```

</details>
````

Notes on the format:
- `<details open>` defaults to expanded; `<details>` (no `open` attribute) defaults to collapsed.
- The `<!-- changetour:hunk … -->` comment is the canonical machine-readable metadata; it's invisible in every renderer.
	- Only `file=` is required.
	- `previousFile` is used to specify the old file path if the file was moved.
	- `highlights` is used to bring attention to particular lines of code in the diff. `new` is used to refer to the modified line numbers and `old` is used to refer to the original line numbers of the diff.
	- `baseBlob` is used for drift detection.
- Blank lines between `<details>` / `<summary>` / metadata comment / ```diff fence are required so GitHub renders the markdown body inside the HTML correctly. The <summary> is to improve default rendering of Change Tour markdown in GitHub.
> **Note on diff bodies that contain ``` lines.** A longer fence length must be used when the patch body contains a triple-or-more-backtick line; the new fence length must be at least one greater than the longest fence length in the diff body.

## Excluding a PR hunk from drift/coverage reports

A tour author may choose to exclude a hunk from their tour. Without a way to opt those hunks out, the drift/coverage tools (`changeTour_getDriftReport` in the extension and `scripts/drift-report-change-tour.js` / `scripts/validate-change-tour.js` in the bundled CLI) would perpetually flag them as `missingInTour` with no corrective action the author can take. Three forms are supported:

**Exact-range** — one PR hunk identified by file + new-side line range:

```
<!-- changetour:exclude file="src/foo.ts" lines="101-120" [fp="..."] [reason="intentionally not narrated"] -->
```

**Whole-file** — every PR hunk in the named file:

```
<!-- changetour:exclude file="src/generated/types.d.ts" [reason="autogenerated"] -->
```

**Glob** — every PR hunk in every file matching the pattern. `*` matches one path segment; `**` matches across segments. No braces, no character classes:

```
<!-- changetour:exclude file="src/generated/**" [reason="autogenerated"] -->
<!-- changetour:exclude file="**/*.d.ts" [reason="generated typings"] -->
```

Attributes:

- `file` (required): a literal repo-relative path OR a glob pattern. Presence of `*`, `?`, or `[` triggers glob matching.
- `lines` (optional): new-side range as `<start>-<end>`. When present, must match the PR hunk's new-side range exactly — copy it from `changeTour_getAvailablePRHunks` or the drift report's `missingInTour` entry. Use `0-0` for a whole-file deletion (the new side has no lines). Omit for whole-file or glob markers.
- `fp` (optional but strongly recommended for exact-range markers): edit-content fingerprint of the hunk. Stable identity primitive that lets the marker survive a PR rebase / surrounding commits that shift the hunk's line numbers — without `fp`, a rebase that bumps the hunk down by even one line invalidates `lines=` and the marker silently stops matching. If omitted, matching falls back to line equality. See [Computing the `fp` attribute](#computing-the-fp-attribute) below for the exact algorithm.
- `reason` (optional but recommended): free-form text. Surfaced inline in the viewer when the **Excluded (N)** filter is selected, so reviewers can see why each hunk was left out.

Exclusion markers only affect the coverage/missing-in-tour calculation.

The markers live in a trailing **appendix** at the end of the file, introduced by an invisible sentinel comment:

```
... your tour content ...

<!-- changetour:excluded-section -->

<!-- changetour:exclude file="src/generated/types.d.ts" reason="autogenerated" -->
<!-- changetour:exclude file="src/old.ts" lines="42-58" reason="deleted in this PR" -->
```

Everything from the `<!-- changetour:excluded-section -->` line to EOF is treated as appendix metadata — exclusion markers and whitespace only, no tour content.

### Computing the `fp` attribute

The fingerprint holds the property that two patches with byte-identical add/remove content fingerprint identically even if the surrounding context lines, the `@@` header, or the line numbers differ. Reducing a hunk to its edit content gives an identity that survives PR rebases and incidental whitespace shifts upstream.

**Output shape.** The fingerprint is exactly **16 lowercase hex characters**, regardless of patch size.

**Algorithm.** Given the unified-diff body of one hunk (including the `@@ -A,B +C,D @@` header):

1. **Extract edit content.**
	1. Split the patch on `\n`.
	2. For each line, strip a single trailing `\r` if present (so CRLF-encoded patches match LF-encoded ones).
	3. Drop the line if it is empty or starts with `@@` (the header — position info, not edit content).
	4. Keep the line only if its first character is `+` or `-`. Discard everything else (context lines starting with a space, `\` no-newline markers, etc.).
	5. Join the kept lines with `\n`. (If the kept list is empty, the patch has no fingerprint — the marker should omit `fp=` entirely.)
2. **Hash the edit content as FNV-1a-64 over its UTF-8 byte representation.**
	1. UTF-8-encode the joined string to get a byte sequence.
	2. Initialize a 64-bit unsigned integer accumulator to the FNV-1a-64 **offset basis** `0xcbf29ce484222325`.
	3. For each byte `b`: `hash = (hash XOR b) * 0x100000001b3`, keeping only the low 64 bits at each step.
	4. Render the final 64-bit value as 16 lowercase hex characters, zero-padded on the left.

FNV-1a is a public, single-pass non-cryptographic hash; UTF-8 is the unambiguous byte encoding. Any language with 64-bit unsigned arithmetic and a UTF-8 encoder reproduces the same output.

**Reference implementation** (TypeScript, sync, runs in browser and Node):

```ts
const FNV_PRIME_64 = BigInt('0x100000001b3');
const FNV_OFFSET_64 = BigInt('0xcbf29ce484222325');
const MASK_64 = (BigInt(1) << BigInt(64)) - BigInt(1);
const TEXT_ENCODER = new TextEncoder();

function editContentFingerprint(patch: string | undefined): string | undefined {
    if (!patch) return undefined;
    const lines: string[] = [];
    for (const rawLine of patch.split('\n')) {
        const line = rawLine.endsWith('\r') ? rawLine.slice(0, -1) : rawLine;
        if (line.length === 0 || line.startsWith('@@')) continue;
        const marker = line[0];
        if (marker === '+' || marker === '-') lines.push(line);
    }
    if (lines.length === 0) return undefined;
    const bytes = TEXT_ENCODER.encode(lines.join('\n'));
    let hash = FNV_OFFSET_64;
    for (let i = 0; i < bytes.length; i++) {
        hash = (hash ^ BigInt(bytes[i])) & MASK_64;
        hash = (hash * FNV_PRIME_64) & MASK_64;
    }
    return hash.toString(16).padStart(16, '0');
}
```

The canonical implementation lives in `src/github/codeTourMarkdown.ts`; the bundled CLI scripts (`scripts/drift-report-change-tour.js`, `scripts/validate-change-tour.js`) ship a byte-for-byte copy. Any third-party tool that wants to write exclusion markers should produce identical output.

**Why this hash?** Three orthogonal decisions, each driven by a constraint:

- **Why non-cryptographic (not SHA-256 / SHA-1)?** `editContentFingerprint` is called synchronously from the parser, and the parser runs both in the extension host and in the webview. The only built-in browser crypto is `crypto.subtle.digest`, which is async — adopting it would force the entire parse pipeline to become async, rippling through every caller. Node's `crypto.createHash` works in the extension host but doesn't exist in the webview. A pure-JS SHA-256 is ~150 lines and slow on multi-thousand-line patches. And we are not defending against adversarial collisions — markers only need to identify hunks within one tour — so cryptographic strength is overkill.
- **Why FNV-1a specifically (not xxHash / Murmur / CityHash)?** All four would work for identity. FNV-1a wins on **portability**: ~10 lines of pseudocode, no SIMD, no precomputed tables, no endianness handling beyond rendering. xxHash and Murmur are significantly faster but each takes ~50–100 lines and a careful port to match a reference. The spec for this attribute is "anyone implementing this in any language should produce byte-identical output" — FNV-1a is the simplest algorithm that meets that bar. Hashing one hunk takes microseconds either way; speed isn't the bottleneck.
- **Why 64-bit (not 32 or 128)?** 32-bit FNV-1a has a non-trivial collision probability once a tour has a few thousand hunks (birthday paradox kicks in around 65K hashes). 64-bit pushes the collision boundary to ~4 billion hashes — comfortably beyond any realistic tour. 128-bit would be safer still, but FNV-1a doesn't have a standard 128-bit form (you'd have to construct one) and the marker would double to 32 hex chars for zero real-world benefit.

**Known weaknesses (and why they don't matter here).** FNV-1a is known to have poor avalanche on small inputs and biased low bits. For an identity primitive on diff content this doesn't matter — we only need equality semantics, not statistical uniformity, and inputs are typically dozens to thousands of bytes, well past the small-input range where the bias is visible. If a future use case ever wanted these fps as e.g. hash-table keys in a hot path with adversarial input, that would be a reason to upgrade.

**Encoding choice.** UTF-8 byte representation is deliberate — JS's native `charCodeAt` is faster but returns UTF-16 code units, which would make the hash JS-specific. Bytes-first is what makes the spec trivially portable to any language with a UTF-8 encoder and 64-bit unsigned arithmetic.

The constants are stated verbatim above (`0xcbf29ce484222325` offset basis, `0x100000001b3` prime) so the spec is self-contained: a third-party tool does not need to know "FNV-1a-64" by name to implement it, only to follow the steps. That insulates the spec from any off-by-one in a future port's named FNV-1a constants.

**Test vectors** for porting:

| Input bytes | FNV-1a-64 (hex) |
| --- | --- |
| *(empty)* | `cbf29ce484222325` |
| `a` | `af63dc4c8601ec8c` |
| `-foo`  *(length 4)* | `a27c0e8fcf2d9f60` |

(Algorithm cross-checks: `fnv-1a` 64-bit over UTF-8 bytes. The empty-input value equals the offset basis, by definition.)
