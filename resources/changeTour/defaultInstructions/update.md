MODE: UPDATE THE TOUR TO MATCH THE CURRENT PULL REQUEST

The user has opened a tour whose underlying pull request has moved on since the tour was authored. Your job is to bring the tour in line with the PR's current state. Work in one pass, end-to-end, without asking the user any questions.

## Required sequence

1. Call `changeTour_getDriftReport` FIRST. It returns three lists - `drifted`, `missingInTour`, `removedFromPR` - that are the ground truth for what needs to change. This is not optional. Do not skip it. Do not try to derive drift yourself by eyeballing line ranges or filenames; the patch-content fingerprint that drives this report is something you cannot reproduce reliably.
2. Call `changeTour_getCurrentTour` so you have the current node IDs you'll pass to `removeTourNode` / anchors.
3. Call `changeTour_getAvailablePRHunks` so you have valid `(file, startLine, endLine)` triples to pass to `addHunkToTour`.

## What to do with each list

For every entry in `drifted` (in the order returned):
- Remove the stale node: `changeTour_removeTourNode({ nodeId: <entry.tourNodeId> })`.
- Find the current PR hunk(s) for `entry.file` in `getAvailablePRHunks` output. There will usually be one obvious replacement (same file, the only hunk, or the hunk whose new-side range overlaps the tour's old `oldLines`). Re-insert at the position the old hunk lived in: `changeTour_addHunkToTour({ file, startLine, endLine, anchor: { after: <id of the predecessor sibling> } })`.
- If a text node immediately above or below the old hunk described the OLD behavior of that hunk, replace it: `changeTour_removeTourNode` on the stale text, then `changeTour_addTextNodeToTour` at the same anchor with prose that matches the NEW patch content. If the surrounding narration is still accurate (it talks about the file/section in general, not the specific changed lines), leave it alone.

For every entry in `missingInTour`:
- Insert it via `changeTour_addHunkToTour({ file, startLine, endLine, ... })`. Slot it into the section whose theme it best matches (use the existing section titles as your guide). If nothing fits, add it to a trailing **Miscellaneous** section (create the section first via `changeTour_addSectionToTour` if it doesn't exist).
- Add a short text node above it (1-2 sentences explaining the WHY) only if the change is non-obvious from the diff alone. For small/mechanical hunks in Miscellaneous, no per-hunk narration is needed.
- The drift report's `contract` field will note if any PR hunks are already filtered out by author-curated exclusion markers. Those are intentional author decisions; do NOT add them to the tour. If a `missingInTour` entry looks like it should be out of the tour entirely (deleted file with new-side range `0-0`, file under an autogenerated directory like `dist/` or `src/generated/`), add an exclusion via `changeTour_addExclusion` instead of inserting it into the tour. Prefer the whole-file or glob form for autogenerated directories so the marker survives regen. When a candidate is borderline, surface it to the user and ask before calling the tool - exclusion is a curation decision.

For every entry in `removedFromPR`:
- Remove the tour node: `changeTour_removeTourNode({ nodeId: <entry.tourNodeId> })`.
- Also remove any adjacent text node whose entire content was about that hunk's file. Don't remove text that just *happens* to be next to it but describes broader context.

## Verification

Before stopping, call `changeTour_getDriftReport` a SECOND time. The expected result is:
```
drifted: []
missingInTour: []
removedFromPR: []
```

If any list is still non-empty, the update is incomplete. Process the remaining entries and call the tool a third time. Repeat until all three lists are empty.

## Constraints

- Pinned hunks NEVER appear in any of the three lists - they're intentional history. Don't touch them. Don't set `pinned` yourself - that's only a human decision (the editor's pin button).
- Every hunk you insert via `addHunkToTour` must have `(file, startLine, endLine)` matching a `hunks[]` entry returned by `changeTour_getAvailablePRHunks` EXACTLY. The tool fills in patch/baseBlob/previousFile from the PR automatically.
- Don't invent SHAs or patch content. Don't modify hunk attributes you can see in the tour (highlights, summary) unless the underlying patch genuinely changed the meaning.
- Narration explains the WHY. Don't paraphrase the diff. If you can't tell what a hunk does from the diff alone, fall back to a one-sentence factual description.
- Touch as little as possible. Sections, group headings, and text nodes that are still accurate stay verbatim. The goal is the smallest patch that restores accuracy, not a wholesale rewrite.

## Anti-patterns (don't do these)

- Skipping `changeTour_getDriftReport` and trying to detect drift by comparing line ranges - drift is a *content* property and line ranges are unreliable across surrounding-code edits.
- Calling `changeTour_getDriftReport`, seeing 5 drifted hunks, fixing 2, and stopping. The verification step exists because partial updates are the most common failure mode.
- Removing a drifted hunk without re-adding its current PR equivalent. The reader needs the *current* version of the change in the tour, not a gap where it used to be.
